## Slide 1

The late delivery the dispatcher never saw
Tokens burned. Time lost. Nothing logged.
Sonakshi Pandey
FE BAR SUBMISSION
A guard model scores every tool call before dispatch and returns a verdict: coerce or allow. On coerce the agent rewrites the bad argument from the server's own declared schema, so the failure and its retry loop are prevented at dispatch rather than diagnosed afterwards.
Head of Delivery Operations: dispatchers get the answer inside the window they can still act in. Platform team: 20.7% of agent spend recovered, $109K/yr. Tool-server owners: which contract to repair first, ranked by dollars, because cost per failed call varies 102x.
THE PROBLEM
A dispatcher asks Tiffin's delivery-routing agent which of a courier's deliveries are running late. They are asking so they can act while there is still time: reroute the courier, warn the customer, comp the order.
One question in twelve runs into a broken MCP tool contract. The agent retries, turns double, and the answer takes 20.6 seconds instead of 8.6 — or never arrives. The courier stays late and nobody is told.
Nothing alerts, because the tool call that failed returned HTTP 200.
TIFFIN
Food-delivery operations  ·  6 AI agents  ·  11 MCP tool servers  ·  1 dispatcher question in 12 comes back blind
THE SOLUTION

## Slide 3

What was observed
163 questions a day come back without a straight answer. Two different people are asking, neither is told that anything failed, and the tool call that broke returned HTTP 200.
THE CUSTOMER ASKS  —  “where is my order?”
113 a day
10,198 of 93,254 Order Support sessions (10.9%) hit a tool call that failed silently. The customer waits 2.4x longer for an answer, or is told something that is not true.
THE DISPATCHER ASKS  —  “which of this courier’s runs are late?”
49 a day
4,439 of 55,723 Delivery Routing sessions (8.0%). In the recorded run the agent reported no late deliveries while D-4410315 was 18 minutes late, and nobody was told.
ON-TIME RATE
163 situations a day that nobody acted on in time.
Every blind question is a courier run or an order whose status reached no one while there was still a window to reroute, warn or comp.
Industry context: food-delivery on-time runs 56–62%, against roughly 95% for general last-mile (npj, 2026). Tiffin operates inside that gap and this is one input to it.
Measured: the blind questions. Tiffin’s own: how many of those reroutes would have landed.
ORDER ACCURACY
The agent does not answer slowly. It answers wrongly.
GUARD OFF  —  “no late deliveries found”, while D-4410315 was 18 minutes late. The page-2 call was rejected and never retried, so the agent answered from half the data.
GUARD ON  —  the malformed argument was coerced from the server’s own declared schema, page 2 came back, and the late delivery surfaced.
Fully measured. No assumption anywhere in this tile.
CUSTOMER SATISFACTION AND CHURN
The driver is measured. The score is Tiffin’s own.
Measured driver: the wait doubles, 8.6s to 20.6s, or the answer is wrong. For a customer asking where their order is, that is the whole experience.
Churn, published rate: 16% of shoppers abandon after a single bad delivery experience, 35% after a late one (Bringg 2026 Delivery Experience Study).
We state the driver we measured, not a satisfaction score we did not.
WHY IT HAPPENS
A broken MCP tool contract is rejected by the server but comes back HTTP 200, so the agent retries blind. Turns 3.82 → 7.47.  Median wait 8.6s → 20.6s.  Cost per question $0.46 → $1.24, of which $1.14 buys nothing.  Nothing alerts.
Measured across 2.6M Gateway OTel spans · 243,112 sessions · 90 days · 6 production agents. Session, wait, turn and cost figures are committed query results in evidence/09_delivery_operations_impact.md and evidence/05_agent_ab_run.md.
What is measured, and what is not: the blind-question counts, the waits, the turns, the costs and the wrong answer above are all derived from the trace corpus. On-time rate and CSAT are Tiffin’s own operating metrics — this slide supplies the input to them and a published rate for churn, not a replacement for the operator’s own coefficient.

The pipeline revealed that the generator's retry signature was wrong.    Training revealed that the pipeline's labels were separable for the wrong reason.    The agent revealed that the model's three-way verdict only had two behaviours behind it.
The loop that actually ran, dozens of times a day: make a change, run it as a real job, read the output, write the output into evidence/. Anything not verified by output was treated as not done.
②  WHERE AI CHANGED HOW THE WORK GOT DONE
③  WHERE I HAD TO OVERRULE IT
Throwaway verification became free.
Two-minute probes you would normally just assume. Three of my assumptions turned out to be wrong.
Claims got re-queried, not remembered.
Every number recomputed rather than recalled. That habit is why evidence/ exists at all.
Attacking my own results became routine.
An early model scored near 1.0 on a random split; treating that as a red flag rather than a win produced the leave-one-bug-family-out protocol.
The deck became code.
Built through the Slides API, so a layout change is a diff instead of an afternoon of dragging boxes.
It built to the checklist.
The first Lakebase layer was a nine-row copy of a Delta table. I cut it. The rebuild was scoped against what inference logs already capture.
It trusted its own synthetic data.
It offered a failure-to-escalation correlation as a finding. That correlation was hand-written into the generator, so reading it back was circular. Kept off this deck.
It measured the wrong thing first.
Summed tool latency made broken sessions look faster, because validator rejections return quickly. The honest measure is turn + tool latency, at the median.
It needed to be told to stop.
A fix-queue panel, a second app tab, a third verdict with no behaviour behind it. All built, all cut.
WHAT IS REAL - every platform component is live on e2-dogfood: AI Gateway OTel span schema · Lakeflow Spark Declarative Pipeline (15 tables) · Unity Catalog · MLflow + UC Model Registry · Model Serving · Lakebase verdict log · Genie space · Databricks App · AI/BI dashboard.
WHAT IS SYNTHETIC - the Tiffin corpus: 2.6M spans generated from a seeded bug registry against the real Gateway span schema. Real shape, fabricated volume, because real Gateway traces are not mine to publish.
The full account, including the trade-offs and what the mistakes above cost, is in BUILD.md and evidence/10_build_process.md.

## Slide 5

Where this goes
The guard reads exactly two things: a Gateway OTel span and the tool server's own declared MCP schema. Nothing in it is Tiffin-specific and nothing is per-agent, which is why it scales sideways with no retraining — enrolment is routing through the Gateway, not integrating with us.
TODAY  ·  one agent guarded
delivery-routing-agent scores every tool call before dispatch. Every verdict lands in the Lakebase verdict log together with whether the call then actually succeeded. Live on e2-dogfood today.
NEXT  ·  all six agents
Same endpoint, same model, no retraining. All six agents already route through the Gateway and all 11 tool servers already publish schemas. Brings the full 20.7% of $528K/yr into scope.
THEN  ·  anything on the Gateway
Any agent built after this inherits the guard on the day it ships. The platform team stops discovering silent tool failures from a cost report.
④  THE CLOSING LOOP  —  the guard is not the end state, it is the instrument that finds the bug

Why the ranking is the point: cost per failed call varies 102x across tool servers, from $2.35 on payment-gateway.create_refund down to $0.023 on merchant-catalog-api.update_merchant. Fixing the most frequent broken contract is not the same as fixing the most expensive one, and the verdict log is what tells them apart.
The number that says it is working: wasted spend falling below 20.7%. If the guard is doing its job, its own coerce volume should shrink over time rather than grow.
THE HONEST LIMIT
The weakest leave-one-bug-family-out fold scores AUC 0.336, below random. The mean of 0.825 is carried by the bug families the model generalises to; it does not generalise to all of them.
So the guard is a first line of defence and not a substitute for repairing tool contracts. That is precisely why the loop above is the plan, and why shipping the guard on its own would not be.
